# Tagalong — repo rules

The product plan is `docs/BUILD_SPEC.md` (Budgetrip + Tagalong). It is the
source of truth: read it before changing anything, build one phase (§9) per
session, then stop. Its §2 principles are rules, not suggestions — in
particular, no price ever comes from the AI, money is integer minor units plus
an ISO 4217 currency, and the budget filter and ranking live in
`packages/shared/src/ranking.ts` with tests.

Read the actual files before changing anything. These are the rules that are
easy to break by accident.

## How work is done: the main session orchestrates, sub-agents build

Standing rule for every session (owner's instruction). The main session is the
**orchestrator**: it never writes product code, tests, docs, plans or designs
itself. It delegates each piece to the roster agent in `.claude/agents/` whose
charter fits, briefs it fully (an agent sees only its brief: goal, spec phase,
files, rules, acceptance check), and integrates the results. It may itself run
read-only commands, git, push, open and merge PRs, and answer questions.

**Default pipeline** for any change to product source:

1. **Plan**: `delivery-lead` (skip only for a single obvious task).
2. **Build**: `backend-engineer` / `frontend-engineer` / `domain-engineer`.
3. **Test**: `test-engineer`.
4. **Verify**: `qa-verifier` (full CI gate + end-to-end where feasible).
5. **Review**, in parallel: `code-reviewer` always; `security-reviewer` for
   auth, sessions, user data, secrets or providers; `pricing-integrity-reviewer`
   for anything touching prices, money, FX, ranking or AI parsing;
   `design-reviewer` for UI. CRITICAL/HIGH findings, and MEDIUM correctness or
   security ones, go back to the owning builder, then re-verify.
6. **Ship**: the orchestrator commits, pushes and opens the PR.

Independent work (disjoint files) runs in parallel; dependent work runs as a
pipeline. Sub-agents never push, open or merge PRs, or change merge rules.
Still one spec phase per session.

| Agent                        | Use it for                                                       |
| ---------------------------- | ---------------------------------------------------------------- |
| `delivery-lead`              | Ordered plan against §9, owners, dependencies, risks (read-only) |
| `backend-engineer`           | `apps/api`: routes, auth, D1, providers, planning, migrations    |
| `frontend-engineer`          | `apps/web`: the React PWA                                        |
| `domain-engineer`            | `packages/shared`: money, types, estimates, candidates, ranking  |
| `test-engineer`              | vitest coverage; never changes product code                      |
| `qa-verifier`                | Full gate + Playwright run, with evidence; no product code       |
| `code-reviewer`              | Correctness, reuse, simplification (read-only)                   |
| `security-reviewer`          | Auth, CORS/CSRF, secrets, scoping, SSRF, prompt injection        |
| `pricing-integrity-reviewer` | No AI prices, minor units + currency, ranking in shared          |
| `design-reviewer`            | UX, price clarity, a11y, phone width                             |

Trivial edits (a typo, a comment) and pure questions may skip the pipeline;
when unsure, it isn't trivial.

## Stack

pnpm workspaces + Turborepo · Cloudflare Worker (Hono) in `apps/api` · Vite +
React web app in `apps/web` (an assets-only Worker) · shared types, money and
ranking in `packages/shared` ·
Cloudflare D1 (`tagalong-db`, binding `DB`) · GitHub Actions for CI, deploy and
auto-merge. Same shape as BVOM.

## Migrations are append-only

Never edit, rename, or delete a migration under `/migrations`. Add a new
numbered file (`NNNN_snake_case.sql`). CI fails the build otherwise
(`scripts/check-migrations-immutable.sh`), and also refuses a `DROP`.

This is what makes "migrate before deploy" safe: the running Worker never sees a
column change underneath it.

## D1

- Always prepared statements with `.bind()`. Never string-interpolate SQL.
- `ON CONFLICT DO NOTHING / DO UPDATE`, never SELECT-then-INSERT.
- Tests run against the real `/migrations` directory in Miniflare.

## Secrets

Never in `wrangler.jsonc`, never committed, never in a client bundle or a
`VITE_` variable. App secrets are set with `wrangler secret put` and persist
across deploys; CI holds only `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`.

## Types

`apps/api/worker-configuration.d.ts` is generated by `wrangler types` from
`wrangler.jsonc` — never hand-edit it. Regenerate after changing bindings
(`pnpm --filter @tagalong/api cf-typegen`) and commit the result.

## Before you push

```sh
pnpm format
pnpm turbo run lint typecheck test build
```

## Merging and deploying (automated)

Work on a feature branch and open a PR. **A PR merges itself** when CI is green
on its current head commit, it is not a draft, it has no `hold` label, and no
review requests changes (`.github/workflows/auto-merge.yml`). The merge then
dispatches `deploy.yml`: gate → D1 migrations → Worker deploy → smoke test.

**The orchestrator merges its own PRs** (owner decision, 2026-11-13: "Just auto
merge going forward"), without asking, including `hold` and guarded-path PRs,
once: CI is green on the current head commit, the PR is mergeable and no review
requests changes; the pipeline above finished clean (no open CRITICAL/HIGH, or
MEDIUM correctness/security, finding); and any ordering dependency is met (e.g.
a binding PR only after the service it binds is merged and live). Never merge
red or incomplete CI, or another session's or person's PR unless the owner
asks. Sub-agents never merge. After merging, confirm the deploy is live and
report what merged.

- Open PRs as **drafts** while work is in progress. Marking a PR ready for
  review is the signal that it may merge.
- Add the `hold` label to destructive data changes, new bindings or secrets,
  CI/workflow changes, and auth or access changes. It stops the workflow merging
  on its own; the orchestrator merges it once the checks above pass.
- Never skip, disable, or weaken a test or a CI check to get green.
- Never push to `main` directly. Once a PR has merged, follow-up work starts on a
  fresh branch from the new `main`.
