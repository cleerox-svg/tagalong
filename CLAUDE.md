# Tagalong — repo rules

The product plan is `docs/BUILD_SPEC.md` (Budgetrip + Tagalong). It is the
source of truth: read it before changing anything, build one phase (§9) per
session, then stop. Its §2 principles are rules, not suggestions — in
particular, no price ever comes from the AI, money is integer minor units plus
an ISO 4217 currency, and the budget filter and ranking live in
`packages/shared/src/ranking.ts` with tests.

Read the actual files before changing anything. These are the rules that are
easy to break by accident.

## Stack

pnpm workspaces + Turborepo · Cloudflare Worker (Hono) in `apps/api` · Vite +
React web app in `apps/web` (an assets-only Worker) · shared types, money and
ranking in `packages/shared` ·
Cloudflare D1 (`tagalong-db`, binding `DB`) · GitHub Actions for CI, deploy and
auto-merge. Same shape as BVOM.

## Migrations are append-only

Never edit, rename, or delete a migration under `/migrations`. Add a new
numbered file (`NNNN_snake_case.sql`). CI fails the build otherwise
(`scripts/check-migrations-immutable.sh`), and also refuses a `DROP`.

This is what makes "migrate before deploy" safe: the running Worker never sees a
column change underneath it.

## D1

- Always prepared statements with `.bind()`. Never string-interpolate SQL.
- `ON CONFLICT DO NOTHING / DO UPDATE`, never SELECT-then-INSERT.
- Tests run against the real `/migrations` directory in Miniflare.

## Secrets

Never in `wrangler.jsonc`, never committed, never in a client bundle or a
`VITE_` variable. App secrets are set with `wrangler secret put` and persist
across deploys; CI holds only `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`.

## Types

`apps/api/worker-configuration.d.ts` is generated by `wrangler types` from
`wrangler.jsonc` — never hand-edit it. Regenerate after changing bindings
(`pnpm --filter @tagalong/api cf-typegen`) and commit the result.

## Before you push

```sh
pnpm format
pnpm turbo run lint typecheck test build
```

## Merging and deploying (automated)

Work on a feature branch and open a PR. **A PR merges itself** when CI is green
on its current head commit, it is not a draft, it has no `hold` label, and no
review requests changes (`.github/workflows/auto-merge.yml`). The merge then
dispatches `deploy.yml`: gate → D1 migrations → Worker deploy → smoke test.

- Open PRs as **drafts** while work is in progress. Marking a PR ready for
  review is the signal that it may merge.
- Add the `hold` label to anything that needs a person to look first:
  destructive data changes, new bindings or secrets, CI/workflow changes, auth
  or access changes.
- Never skip, disable, or weaken a test or a CI check to get green.
- Never push to `main` directly. Once a PR has merged, follow-up work starts on a
  fresh branch from the new `main`.
